# Testing

## Current state

GitHub Actions runs the quality workflow on every pull request, as two parallel jobs. Pushes do not run it; merged code is checked by its pull request:

- **PHP** — on the minimum supported PHP version (8.3) and the newest stable one (8.5), as set out in [Platform support](support.md): installs locked Composer dependencies, runs PHP syntax checks, PHPCS, and the focused PHPUnit regression tests.
- **Node** — on the version in `.nvmrc`: installs locked npm dependencies, runs the Vitest unit tests with coverage (totals in the job summary and the HTML report uploaded as the `unit-coverage-<run id>` artifact; there is no threshold yet), type-checks, lints JavaScript/TypeScript and SCSS, builds the theme and creates `dist/` in one step, and verifies required package paths.

`src/scss/foundations.test.ts` compiles the global stylesheet and the affected block stylesheets with Sass and reads them through the CSSOM: links are underlined with no global rule removing it, no global rule removes `ul`, `ol` or `li` markers, `:focus-visible` draws the focus-ring tokens in the highlight colour, smooth scrolling is set only under `prefers-reduced-motion: no-preference`, the reduced-motion rule in the reset layer switches off transitions, animations and smooth scrolling with `!important`, each navigation and component list removes its own markers in its block's layer, content lists keep bullets and numbers, and buttons opt out of the link underline. `SkipLinkTargetTest` checks every template has exactly one `<main>` Group block and that `jmc_main_skip_link_target()` gives only the main group `tabindex="-1"`.

`tests/e2e/axe.spec.ts` runs [axe](https://github.com/dequelabs/axe-core) (`@axe-core/playwright`) against the WCAG 2.0–2.2 A and AA rules and axe's best-practice rules, in every browser the suite runs. It builds a site from the theme's patterns — a static front page (`jmc/home-page`), a standard page with the template title (service introduction, why choose us, contact details and call-to-action patterns), the Services landing page and one service beneath it, and the Contact page — fills in the business details, and fills in the header and footer template parts as the Site Editor does: a menu with a submenu in each, a header call to action and a credential logo (the e2e logo fixture). It then scans the front page, standard page, Services landing page, single service page, Contact page, a search (answered by the 404 template, since search is turned off) and a missing page at 1280px; the mobile menu open with its submenus expanded at 375px; a desktop submenu opened by keyboard; and the enquiry form's error summary after an empty submission and its no-JavaScript "sent" and "invalid" notices. Together these render every custom block. Scans run with reduced motion, so colours are never measured mid-transition. A serious or critical violation fails the test, listing for each rule its impact, help link and every failing element's selector, markup and what to fix; minor and moderate violations are added to the report as annotations, and the full results are attached to each test. Accepted violations are recorded in `tests/e2e/accessibility-exceptions.ts` (see [Accessibility exceptions](accessibility.md#accessibility-exceptions)), and the spec fails once an exception's review date has passed. Setup restores the options it changes and deletes its pages, menus, logo and template parts afterwards; it refuses to run if the header or footer is already customised in the Site Editor.

Broader WordPress integration coverage and visual-regression tests are not yet configured, and axe does not yet scan editor states. Static quality gates and focused regression tests do not replace full behavioural verification.

### Console and PHP errors

Specs import `test` and `expect` from `tests/e2e/fixtures/test.ts`, never from `@playwright/test` or `@wordpress/e2e-test-utils-playwright` directly. Its automatic fixtures apply to every test without opting in:

- **Browser errors** — `console.error()` messages (including failed resource loads) and uncaught exceptions or unhandled rejections from any page in the test's browser context fail that test. The failure lists each error with its page URL, source location or stack, and attaches `browser-errors.json` to the report. Pages in a context a test creates itself with `browser.newContext()` are not watched.
- **PHP errors** — `.wp-env.json` turns on `WP_DEBUG` and `WP_DEBUG_LOG` (with `WP_DEBUG_DISPLAY` off, so errors never reach the page) and maps the log to `artifacts/e2e/php/debug.log` on the host. A PHP fatal, parse, warning, notice or deprecation entry (including `_doing_it_wrong()` and `trigger_error()` output) or a `WordPress database error` logged while a test runs fails that test, with the log entries in the message and attached as `php-errors.log`. Requests from the browser and `wp-env run cli` commands both count.

Global setup (`tests/e2e/setup/global-setup.ts`) checks that WordPress writes to that log and empties it, so a misconfigured environment fails at once rather than passing silently; restart with `npm run env:start` after changing `.wp-env.json`. Global teardown (`tests/e2e/setup/global-teardown.ts`) fails the run if the log holds any PHP error at the end, which also catches errors raised in `beforeAll`/`afterAll` hooks and in tests that passed on a retry. In CI the PHP log is uploaded with the failure evidence.

A test that provokes a browser error on purpose allows it for itself:

```ts
test.use( {
	allowedBrowserErrors: [
		{
			pattern: /Failed to load resource/,
			reason: 'The test stubs a 500 response.',
		},
	],
} );
```

Errors allowed in every test are listed, each with a reason, in `tests/e2e/fixtures/allowed-errors.ts`. Keep this table in step with that file:

| Kind    | Message                                                                                 | Reason                                                                                                                                                                                                                                                                                                 |
| ------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Browser | `Prefetch request denied: URL must be secure (HTTPS)`                                   | WebKit refuses the prefetches requested by WordPress core's speculative loading on a non-HTTPS origin. `wp-env` serves plain HTTP; production uses HTTPS.                                                                                                                                              |
| Browser | `NS_BINDING_ABORTED` from `chrome://juggler/`                                           | Playwright's Firefox automation layer logs a worker request it aborted when a test navigates away. It comes from the test harness, not the page.                                                                                                                                                       |
| Browser | `XMLHttpRequest` or `Fetch API cannot load <test site>/… due to access control checks.` | WebKit reports a request it cancels because the page navigated away (dashboard widgets, editor previews) as an access-control error. Requests to the test site's own origin are never subject to CORS, so on that origin the message only means a cancelled request. Cross-origin failures still fail. |

Tests that request a missing page on purpose (the 404 and search checks in `templates.spec.ts` and `axe.spec.ts`) also allow `notFoundPageLoadError` from the same file, the `Failed to load resource: … status of 404` message Chromium and WebKit log for that response. It is not allowed globally, because a 404 anywhere else is a broken link or asset.

No PHP log entries are allowed. Fix the cause rather than allow-listing it; add an entry only for noise the theme cannot fix, with a pattern as narrow as possible.

## PHP regression tests

PHPUnit configuration is defined in `phpunit.xml.dist`. PHP tests and their isolated WordPress test doubles live under `tests/phpunit/`.

Run the PHP test suite with:

```bash
composer test
```

Render regression tests must exercise omitted, default, supported, and deliberately malformed attribute values where applicable. PHP notices and warnings should cause test failures.

`tests/phpunit/bootstrap.php` loads the real, WordPress-independent theme helpers (`inc/helpers/component-args.php`, `inc/helpers/html/attributes.php`, `inc/helpers/link.php`, `inc/helpers/navigation.php`, `inc/helpers/text.php`, `inc/helpers/contact.php`, `inc/helpers/button.php`, and `inc/helpers/enquiry.php`) rather than duplicating them, so render tests exercise production attribute handling. It also provides WordPress test doubles: `esc_attr()`, `esc_html()`, and `esc_html_e()` HTML-encode their input so tests can assert escaped output, and `jmc_component()` includes the component template directly with `$args` in scope. `esc_url()` strips encoded line breaks (`%0D`, `%0A`) as core does and otherwise returns its input unchanged, so assert URL safety through theme validation such as `jmc_safe_link_url()`. Footer tests use further doubles: `get_post()` reads fixtures from `$GLOBALS['jmc_test_posts']`, `parse_blocks()` decodes `post_content` stored as JSON-encoded parsed blocks, `is_page()` compares against `$GLOBALS['jmc_test_current_page']`, `wp_get_icon()` returns a placeholder SVG recording the icon name for the icons the theme uses, and `home_url()` and `__()` return fixed or untranslated values. Render tests pass block context as `$block = (object) [ 'context' => … ]`. Legal and menu tests add: `get_posts()` filters the `jmc_test_posts` fixtures by `post_type`, `name`, `post_parent`, and `post_status`, returns every match when `posts_per_page` is `-1`, and records each query in `$GLOBALS['jmc_test_get_posts_queries']`; `get_bloginfo()` reads `$GLOBALS['jmc_test_bloginfo']`; `wp_date()` formats a fixed time in 2030; `get_option()` and `update_option()` use `$GLOBALS['jmc_test_options']`; `wp_insert_post()` records posts in `$GLOBALS['jmc_test_inserted_posts']`; and `add_action()` records hooks in `$GLOBALS['jmc_test_actions']`. ## Accessibility release matrix

Automated scans cannot validate reading order, usable focus, meaningful alternative text, or sensible assistive-technology output. At every release candidate, run the whole [manual accessibility QA checklist](accessibility-qa.md) on staging, on each keyboard-only and screen-reader setup it lists, and record the results in `docs/accessibility-qa/v<version>.md` from its [template](accessibility-qa/template.md). The checklist marks the checks the automated suites already cover.

## Compatibility and package verification

Test the supported WordPress release and the lowest supported PHP version declared in `style.css`, plus the current production target. Update `Tested up to` only after testing that WordPress release, following the upgrade steps in [Platform support](support.md#upgrades).

CI currently verifies that required files exist in `dist`; it does not install or activate the package in WordPress. Before release:

1. Produce `dist/` with `npm run package`.
2. Archive the packaged theme directory.
3. Install it in a clean supported WordPress environment without source dependencies.
4. Activate it and open the Site Editor and frontend.
5. Render all custom blocks and representative templates.
6. Confirm CSS, scripts, fonts, images, components, templates, and PHP includes load.
7. Review PHP logs and the browser console.

A working development checkout is not evidence that the distributable package works.
